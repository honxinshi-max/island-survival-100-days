# UI 设计

## 1. 设计目标

UI 的首要任务不是展示世界观，而是让 3—5 人在每个决策时刻看清：现在能做什么、要付什么、何时结算、失败会失去什么、这一步是否锁死百日救援路线。桌面卡牌原型和数字实现应共享同一信息架构。

## 2. 主界面信息层级

### 顶部：时间与全局风险

- 当前天数、白天/夜间、信标当前状态与按连续广播数重算的最迟有效广播日；
- 今夜事件/危机预告及可信度；
- 天气 W、岛屿特性、难度倍率；
- 团队从当日至终局夜是否仍满足四账可胜性；材料、行动、生存、能源/可达分别显示“通过/缺口/待确认”，不得把缺失数据画成通过。

### 左侧：角色区

每名角色显示生命、行动点、已预支行动、饱腹、水分、体温、伤势、疾病、装备耐久和职业能力。状态悬停或展开后必须显示下一结算时点与具体后果，不能只用颜色。

### 中央：岛屿与行动区

- 区域连接、当前角色位置、移动成本、已发现/未发现状态；
- 资源点当前/初始储量、恢复类别、下次恢复日；
- 可执行行动卡必须同时显示行动点、工具耐久、目标值、材料、预期进度和失败损失；
- 禁用行动保留可见，并给出唯一主因和所有次因。

### 右侧：营地与项目区

- 建筑按完好/受损/停机显示，不只显示耐久数字；
- 当日可用能源、跨夜保留上限、已登记设备及占用原因、今夜能源承诺；
- 项目材料是否已支付、当前里程碑、该段难度、进度和取消返还；
- 信标五段不得把跨段进度画成连续无边界进度条。

### 底部：决策与日志

- 当前检定公式和每个加减值来源；
- 结果等级、进度、消耗、耐久和状态变化；
- 可展开的夜间 7 步日志；
- 撤销只允许在尚未揭示随机结果、未影响其他玩家信息时使用。

## 3. 关键流程

### 日间计划

团队先看“必须支付”清单，再分配角色行动。系统应提示材料够但行动/能源/路线不够的假可行方案，不能只检查背包材料。

### 项目检定

确认框依次展示：当前里程碑 → 目标值 → 执行者/协助者各自行动成本 → 首次掷骰前支付的材料与样本 → 可能进度。若本次进度超过段需求，V1.3.1 明确提示“超出部分丢弃、不结转”。

### 夜间结算

按固定 7 步逐项动画/卡牌结算；第 1 步内部依次为“自动防御能源承诺 → 普通事件 → 已取得的危机预防 → 保留危机的应对/止损 → 其余营地防御战”，每一步可快进但不可打乱。灾害摧毁发电设备后，信标广播失败必须引用同夜第 1 步的具体原因。

### 濒死救治

清晨界面按“状态结算 → 行动计算 → 紧急救治 → 死亡 → 资源恢复 → 建筑产出 → 驯兽处理”显示队列；救治面板要显示每名救治者是否已用预支救治、当日剩余行动和未救治角色的死亡时点，禁止同一行动点被多次选择。

### 终局结算

第 100/20 夜在夜间第 1—6 步后进入单独的“终局健康闭合”画面，只显示状态伤害、紧急救治、死亡和一次性胜负判定。界面不得生成第 101/21 天的资源或建筑产出，也不得提供继续建造、治疗或广播来改判的按钮。

## 4. 可访问性

- 状态不能只依赖红/绿；同时用文字、图标和纹理。
- 全部操作可由键盘/手柄到达；焦点顺序与日间计划顺序一致。
- 骰点和状态变化提供文本日志，屏幕阅读器只播报变化，不逐帧重播。
- 可关闭摇晃、闪烁和高频音效；危机倒计时不只靠声音。
- 关键数值使用可缩放字体；四人角色区在窄屏改为分页，不压缩到不可读。

## 5. 试玩数据面板

每局结束只要求 10 项：人数职业、救援结果、稳定饮水/食物天数、信标关键日、五类生命损失、首次枯竭、设备关机、角色行动贡献和三个“没有真实选择”的时刻。首次稳定饮水/食物日统一指：从该日开始做一次连续 3 天无随机投影，每天均能满足当时存活人口且不重复使用投入；直到终局都未出现时记“未达成”。面板展示原始数，不自动把相关性写成因果。

## 6. 验收标准

- 玩家无需查规则书即可解释为什么行动不可用或为何广播中断；
- 任意项目都能追溯材料、行动、检定和进度；
- 资源点 0 与 1 不形成隐藏规则套利；
- 建筑 1 耐久不会看起来与满耐久同效；
- 最终校准至少显示并结算一次难度 11 检定；
- 项目第一次失败不能回滚为未支付材料，协助者的行动必须进入日志；
- 受损基础效果 1 显示为 0，二元能力显示“受损不可用”或卡牌覆盖来源；
- 评分使用全图可再生点分母，未探索点不能从分母消失；
- 结算画面稳定时不反复重建内容或重复播报。
- 终局只出现一次结果；第 101/21 天的生产、治疗或广播不能改变胜负。
